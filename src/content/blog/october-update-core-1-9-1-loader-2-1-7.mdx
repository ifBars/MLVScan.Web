The October 28 releases bring better command recovery and more precise handling
of legitimate behavior. The goal is to give people a more useful explanation of
what a mod does, while keeping dangerous possibilities visible.

## A restart can deserve a warning without being blocked

Launching another process is worth inspecting. It can also be part of a mod's
restart feature, which makes a blanket rule frustrating for both players and
authors.

Core 1.9.1 recognizes a narrowly supported local restart-script pattern. When
the written script and its launcher can be connected, and the script matches
the supported operations, the result can stay **Suspicious** with a non-blocking
recommendation. Loader 2.1.7 respects that recommendation and still shows an
advisory in its console and report.

That doesn't turn every restart script into an allowed exception. Unresolved
launch bindings, extra risky operations, incomplete analysis, or a known threat
match prevent this advisory treatment. It also isn't a clean verdict for the
rest of the assembly.

## More of the command is visible

Malicious code doesn't always hand a complete command to the process launcher.
Parts may be encoded, transformed, returned by a helper, or written into a
script first.

The new Core release follows more supported encoding and string-transform
chains, recovers encoded commands, and exposes supported bound script bodies
to detection and reporting. DevCLI 1.3.1 makes that recovered evidence easier
to inspect in its output.

When a value has several possible sources, the scanner retains those alternatives
within its analysis limits. A harmless-looking candidate doesn't erase another
candidate that could launch a dangerous target or write to a persistence path.
Values that depend on runtime input can still remain unresolved.

## Deep analysis still has limits

Core's configurable deep analysis arrived in 1.9.0. Version 1.9.1 extends the
larger budgets to process-value recovery too. DevCLI's retry and deep modes can
use those budgets, and report when a limit is still reached.

More analysis can take longer, and it doesn't make ambiguous runtime values
certain. A partial result needs to stay visibly partial.

## What changes when you update?

Loader 2.1.7 includes builds for MelonLoader, BepInEx 5, BepInEx 6 Mono, and
BepInEx 6 IL2CPP. It also carries the blocking recommendation through the signed
scan cache. Older cache entries are invalidated and rescanned.

There's one detail for CI users: DevCLI's classification gate is unchanged.
A `Suspicious` result still fails a `--fail-on-disposition Suspicious` check,
including an advisory result that the loader wouldn't block. Automation that
intends to follow the blocking recommendation needs to read
`disposition.blockingRecommended` from the schema report instead.

MLVScan still uses static analysis. These changes improve the evidence and the
decision around it; they don't guarantee that every command can be recovered
or that a mod is safe.
